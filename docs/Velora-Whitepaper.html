Section 01

01Executive Summary

Velora is a home-services marketplace that replaces a fragmented list of contacts—an interior designer here, a plumber's cousin there—with one trusted platform covering every trade a home needs.

Vision

A world where getting home work done—big or small—is as simple, transparent, and trustworthy as ordering anything else online.

Mission

Connect customers with verified professionals across every home-service trade, and give both sides a single, transparent booking-to-completion workflow.

Target Users

Homeowners planning anything from a full room redesign to a same-week repair; independent professionals—designers, painters, plumbers, electricians, carpenters—seeking steady, trustworthy demand.

Section 02

02Problem Statement

Today, getting home work done means juggling disconnected people, channels, and promises — with no single place to track any of it.

Today's ProblemWhat it looks likeHow Velora solves it
Multiple, disconnected vendors A different contact for design, painting, plumbing, electrical—each found separately, each trusted on faith. One platform, one account type (PROFESSIONAL) spanning every trade — find and book any of them the same way.
Lack of transparency Verbal quotes, no itemized breakdown, price surprises mid-project. Structured, itemized Quotations the customer explicitly accepts or rejects before work starts.
Difficult project tracking Status lives in someone's memory or a WhatsApp thread. Every booking has an explicit, queryable state (PENDING → CONFIRMED → COMPLETED).
Poor communication Calls and texts scattered across channels, nothing recorded. Structured requests replace ambiguity — category, style, budget, and location are captured up front.
No single platform for both scales A full renovation and a leaky tap need entirely different vendor-finding processes today. Both are first-class request types on the same platform — see Section 3.
Trust issues No visible track record before hiring someone into your home. Public professional profiles, portfolios of real past work, and a rating built from completed-booking reviews.
Section 03

03Product Vision

Velora is a one-stop home services platform. Every request a customer makes falls into one of two journeys — both converge on the same underlying account, portfolio, and booking model.

flowchart TD
    H[Customer need] --> D{Scale of the job?}
    D -->|"End-to-end room /\nhome transformation"| A[Complete Home Transformation]
    D -->|"Single, standalone\ntrade job"| B[Individual Home Service]
    A --> C1[Shared: Professional accounts]
    B --> C1
    C1 --> C2[Shared: Booking lifecycle]
    C2 --> C3[Shared: Quotation & Review]
    C3 --> E[Completed, reviewed work]
Both journeys are different front doors into one shared backend model.
Complete Home TransformationIndividual Home Service
ExampleFull living-room redesign with a chosen interior designerFix a leaking pipe, repaint a wall, rewire a switch
Professional pickCustomer can browse & choose directly, or ask Velora to assignAlways Velora-assigned — matched by trade & location
Portfolio relevanceHigh — style and past work drive the decisionLower — trade skill and availability matter more than style
Request typeFULL_HOME_PROJECTINDIVIDUAL_SERVICE
Why both exist
Splitting these into two entities would have meant two account types, two portfolio models, two booking pipelines — double the code, double the ways for the two to drift apart. Instead, one RequestType on Booking and one ServiceGroup on Category route the same underlying model down two different rule sets. A professional never has to pick which "kind" of platform they're on — a carpenter and an interior designer are both simply PROFESSIONALs.
Section 04

04User Roles

Three roles, one account table — a user is exactly one of these, enforced at both the database and API layer.

👤 Customer

  • Browse professionals & portfolios
  • Book a Full Home Project (direct pick or Velora-assigned) or an Individual Service
  • Review a sent quotation — accept or reject
  • Cancel a booking before completion
  • Leave a rating & review after completion

👷 Professional

  • Maintain a public profile (bio, specialization, city, availability)
  • Upload portfolio items showcasing past work
  • Manage assigned bookings through their lifecycle
  • Draft, send an itemized quotation
  • Update booking status (confirm, complete)

🛡️ Admin

  • View ranked, scored professional candidates for unassigned bookings
  • Assign a professional to a booking
  • Oversees the trust & matching layer of the platform
  • Not self-registrable — seeded/provisioned only

Section 09

09Architecture

A conventional, deliberately boring layered backend — boring is a feature when the goal is a codebase any engineer can pick up quickly.

flowchart TD
    C["Controller\nHTTP mapping, role checks (@PreAuthorize), request validation"] --> M["Mapper\nEntity ⇄ DTO conversion"]
    M --> S["Service\nBusiness rules, state-transition validation, @Transactional"]
    S --> R["Repository\nSpring Data JPA — derived methods & Specification joins only"]
    R --> DB[("PostgreSQL\nhosted on Neon, schema owned by Flyway")]
Every request flows top to bottom — no layer is ever skipped.

Why Clean Architecture

Controllers never see entities and services never see HTTP concerns — each layer can change independently. A new frontend, or a switch from REST to GraphQL, would only touch the controller layer.

JWT Authentication

Stateless bearer tokens — no server-side session store, so the API scales horizontally with zero session-affinity concerns.

Role-Based Authorization

@PreAuthorize("hasRole('X')") on every state-changing endpoint — enforced at the method level, not left to controller-body if checks that are easy to forget.

Section 11

11Important Design Decisions

Every major structural choice, and the reasoning behind it.

Why "Professional" instead of only "Designer"?
Alternative considered
Keep the account type narrowly named "Designer," add separate account types per trade later.
Chosen approach
One PROFESSIONAL role from the start — a painter, plumber, or designer is the same kind of account, distinguished by profile data, not by schema.
Why support both Full Projects and Individual Services?
Alternative considered
Two separate booking systems, or two separate apps.
Chosen approach
One Booking entity with a requestType flag — shared lifecycle, shared quotation/review flow, different validation rules per type.
Why do Portfolios exist as a separate concept from bookings?
Alternative considered
Attach past-work images directly to the professional profile as a flat list.
Chosen approach
A first-class PortfolioItem catalog — searchable, filterable, sortable, and reusable as evidence in the matching algorithm.
Why split interior-design fields into a satellite table?
Alternative considered
A generic JSON metadata blob on every portfolio item; or keep style/price on the base table.
Chosen approach
Optional InteriorDesignDetails 1-to-1 satellite — keeps every trade's item the same shape while preserving typed, filterable search for interior design specifically, with zero schemaless data.
Why JWT instead of server-side sessions?
Alternative considered
Session cookies backed by a server-side session store.
Chosen approach
Stateless JWT bearer tokens — no session affinity, the API scales horizontally without shared session state.
Why role-based security at the method level?
Alternative considered
Manual role checks written inside each controller method body.
Chosen approach
@PreAuthorize declared on the endpoint itself — the rule is visible at a glance and can't be silently skipped.
Why a strict layered architecture?
Alternative considered
Fat controllers that talk to repositories directly for "simple" endpoints.
Chosen approach
Controller → Mapper → Service → Repository, always — consistency means any engineer can predict where logic lives.

Section 13

13Security

Stateless, token-based authentication with method-level role enforcement on every write operation.

sequenceDiagram
    actor U as User
    participant API as API
    participant Auth as AuthService
    participant Filter as JwtAuthFilter
    participant Svc as Protected Endpoint

    U->>API: POST /auth/login (email, password)
    API->>Auth: verify credentials (BCrypt compare)
    Auth-->>U: JWT access token

    U->>API: Request + Authorization: Bearer <token>
    API->>Filter: validate token signature & expiry
    alt Token valid
        Filter->>Svc: forward request, principal attached
        Svc-->>U: 200 + response
    else Token invalid/missing
        Filter-->>U: 401 Unauthorized
    end
ControlHow it works
Password hashingBCrypt — passwords are never stored or compared in plain text.
Token validationEvery request (except public routes) passes through a JWT filter that checks signature and expiry before reaching a controller.
Role-based authorization@PreAuthorize("hasRole('X')") on each state-changing endpoint — CUSTOMER, PROFESSIONAL, and ADMIN each see only what their role permits.
Public endpointsAuth (register/login), catalog browsing (GET /portfolio, /categories, /professionals/{id}) — explicitly allowlisted, everything else defaults to requiring authentication.
Request validationBean Validation (@NotNull, @Size, @DecimalMin, etc.) on every incoming DTO — malformed requests are rejected before touching business logic.

Section 15

15Conclusion

The Velora MVP is small on purpose — and shaped so that "small" never means "narrow."

What's shipped
A working marketplace: any home-service professional can be discovered, booked, quoted, and reviewed, across two distinct journeys that share one account model, one portfolio model, and one booking lifecycle.
Why it scales
Every structural decision in this document — one PROFESSIONAL role instead of per-trade accounts, one Booking with a requestType instead of two systems, an optional satellite table instead of rigid columns — exists specifically so that the next trade, the next journey, or the next feature slots in without reshaping what's already there. The roadmap in Section 14 is not a rewrite plan; it's a list of additions.

Velora starts as a trustworthy way to book anyone from an interior designer to a plumber. The architecture behind it is built to become the operating system for how a home gets taken care of.
